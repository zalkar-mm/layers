# Процесс работы

Смежные темы: [review.md](review.md), [testing.md](testing.md). Роли субагентов и порядок шагов — `.claude/agents/frontend-developer.md` §5.

## 1. Иерархия работы

| Уровень | Что это | Правило |
|---|---|---|
| **Этап** | Этап ТЗ (§2, 0–13) | Строго по порядку. Следующий — только после подтверждения пользователя |
| **Коммит** | Законченная часть этапа | Проходит `yarn check`. Один смысл — один коммит |
| **Шаг** | Действие внутри работы агента | Не коммитится |

Размер коммита: 5–50 строк — норма; больше 200 — дробим; меньше 5 — объединяем с соседним. Коммит, который ломает сборку или тесты, — плохой коммит.

## 2. Порядок внутри этапа

1. Прочитать правила и критерии этапа в ТЗ, назвать их номерами.
2. Если этап меняет правила — **первым коммитом** `docs(rules): …`, до кода.
3. Типы и контракты → тесты (для логики — падающие) → реализация → UI снизу вверх.
4. Все состояния данных проверены (idle, loading, loading со stale, success, error, error со stale).
5. `yarn check` зелёный, для UI-этапов плюс `yarn e2e`.
6. Ревью diff по [review.md](review.md).
7. Запись в `AI_LOG.md`, ADR если было архитектурное решение.

## 3. Коммиты

Conventional Commits, **описание на русском**, с маленькой буквы или с большой — не важно (`subject-case` отключён).

```
feat(entities/layer): машина состояний слоя
fix(features/layer-control): ответ устаревшего запроса попадал в кэш
test(features/layer-control): сценарии гонок R1–R9
docs(rules): правило про мемоизацию
```

| Тип | Когда |
|---|---|
| `feat` | Новое поведение |
| `fix` | Исправление поведения |
| `refactor` | Изменение кода без изменения поведения |
| `perf` | Производительность, с замером в теле коммита |
| `test` | Только тесты |
| `docs` | Документация, правила, ADR, `AI_LOG.md` |
| `style` | Форматирование |
| `build` / `ci` | Сборка, зависимости / пайплайн |
| `chore` | Прочее обслуживание |

Scope — путь слайса (`entities/layer`) или область (`rules`, `infra`, `e2e`). Тело коммита — место для обратимых технических решений и их причин.

Коммитить — только если пользователь разрешил коммиты в этой сессии.

## 4. Проверки

| Когда | Что запускается |
|---|---|
| pre-commit | lint-staged: ESLint `--fix` + Prettier на изменённых файлах |
| commit-msg | commitlint |
| pre-push | `yarn typecheck && yarn test` |
| Перед сдачей этапа | `yarn check` (+ `yarn e2e` для UI) |
| CI | lint, lint:fsd, typecheck, test, build, e2e |

Хуки не обходятся (`--no-verify` запрещён).

## 5. Изменение правил

- Правило меняется отдельным коммитом `docs(rules): …` **до** кода, который на него опирается.
- Поменял конфиг линтера — обнови соответствующий раздел «Что запрещено» в том же коммите.
- Нашёл расхождение правил с кодом — [README §3](README.md#3-расхождения).

## 6. Зависимости

- Версии фиксируются **точно**, без `^`. Lockfile в репозитории.
- Новая зависимость вне списка из `.claude/agents/frontend-developer.md` §3 — только с обоснованием и после подтверждения пользователя.
- Yarn 4 не ставит версии младше 24 часов (`npmMinimalAgeGate`, защита цепочки поставок). Карантин не обходим — берём предыдущую версию и пишем об этом.
- Установка — через `yarn add -E`, никогда не правкой `package.json` руками.

## Что запрещено

- ❌ Начинать следующий этап без подтверждения текущего.
- ❌ Коммит, который не проходит `yarn check`.
- ❌ `--no-verify`, отключение хуков.
- ❌ `^`/`~` в версиях, зависимость без согласования.
- ❌ Коммит без разрешения пользователя.
