## 0. Прочитать первым: что на самом деле проверяют

Тестовое выглядит как «три чекбокса и слайдер», но интерфейс тут вторичен. Сами авторы пишут: «внешний вид не важен». Проверяют четыре вещи:

| # | Что проверяют | Как ревьюер будет это проверять |
|---|---|---|
| 1 | Управление состоянием в **vedro** | Откроет стор и посмотрит, где живёт логика: в компонентах или в отдельном слое |
| 2 | Асинхронность и **гонки** | Быстро пощёлкает тумблер и посмотрит, не «мигнёт» ли устаревший результат |
| 3 | **Отсутствие лишних рендеров** | React Profiler / React DevTools «Highlight updates» при движении слайдера |
| 4 | **Масштабирование 5 → 100+** | Прикинет, что будет со стором и списком при 100 слоях |

Плюс строгая типизация без `any` и README: архитектура и то, **как именно** помог AI.

Цель — не просто закрыть эти пункты, а **доказать** каждый: тестом, счётчиком, замером, демо. Ревьюер не должен верить на слово — он должен увидеть.

### Главное ограничение: «без избыточного усложнения»

Это прямая цитата из вакансии. Каждое архитектурное решение сверх минимума должно иметь в README одну строку «зачем» и, где можно, цифру. Если обоснование не пишется — решение убираем.

### Что уже известно про vedro (проверено на исходниках v1.1.0)

`vedro` — малоизвестная библиотека (GitLab `grizzzly/vedro`). Скорее всего, внутренний или «свой» инструмент команды. Разбор её исходников — это ровно тот навык, который вакансия называет «самостоятельно исследовать незнакомую технологию». Найденное **обязательно** использовать в решении и README.

| # | Факт | Следствие для решения |
|---|---|---|
| V1 | `dispatch(async cb)` — возвращаемое значение async-колбэка **теряется**. Проверка `isAsyncFunction` сделана как `fn instanceof Promise`, что для функции всегда `false` | Async-dispatch vedro **не используем**. Асинхронщина живёт в командах, в стор пишем синхронным `dispatch` |
| V2 | Добавить новый ключ верхнего уровня через колбэк или объект нельзя: `"Dispatch callback have returned wrong object"`. Строковая форма `dispatch(key, value)` ключи не проверяет и новый ключ добавляет | Слои лежат в `byId: Record<LayerId, LayerState>`, а не отдельными ключами стора |
| V3 | Штатный `useSelector` на **каждый** dispatch вызывает **все** селекторы и сравнивает результаты через `JSON.stringify` | O(N) с дорогой константой. Для строк слоёв пишем свой хук (§4.3) |
| V4 | `useSelector` подписывается в `useEffect` с `[]` | 1) селектор «замерзает» на пропсах первого рендера; 2) обновление между рендером и подпиской теряется (tearing). Свой хук строим на `useSyncExternalStore` |
| V5 | `useDispatch` возвращает новую функцию на каждый рендер (`.bind`) | Dispatch не передаём пропсами. Компоненты вызывают команды-модули напрямую |
| V6 | Повторный вызов unsubscribe у `@state` удаляет **чужого** подписчика (`splice(-1, 1)`) | Unsubscribe идемпотентный — оборачиваем в guard |
| V7 | `store.on(key, cb)` позволяет подписаться вне React. Колбэк вызывается сразу при подписке и на каждый `dispatch` с этим ключом, даже без смены ссылки | Синхронизация с картой идёт без React-рендеров (§9), сравнение слоёв по ссылке делает MapSync |
| N1 | `get()` без ключа возвращает новую копию состояния на каждый вызов; `get(key)` — стабильную ссылку | `getSnapshot` хуков берёт `get('byId')`, а не `get()` (§4.3) |

**Статус находок.** Все находки V1–V7 и N1 подтверждены тестами на React 19.3 + vedro 1.1.0 (Vitest + jsdom) в задаче 0.8. Итоги, ссылки на строки исходников и уточнения — `docs/vedro-findings/README.md`.

| Правило | Значение |
|---|---|
| Находку опровергли | Удаляется из README и письма. Обход, если он не нужен, убирается из кода |
| Находку подтвердили | Появляется минимальный репро-тест в `docs/vedro-findings/`, ссылка на него — в README |
| Формулировки | Нейтральные: «поведение», «ограничение», «как обойдено». Без оценок библиотеки |

## 2. Порядок работ

Этапы идут строго по порядку: каждый следующий опирается на предыдущий. **Логика и тесты — раньше UI.** Это сознательно: если начать с интерфейса, гонки придётся отлаживать руками.

| Этап | Что | Результат этапа |
|---|---|---|
| 0 | Каркас репозитория, CI, пустой деплой, проверка находок vedro | Зелёный пайплайн, живая ссылка, подтверждённый список V1–V7 |
| 1 | Доменная модель и реестр слоёв | Типы + конфиг 3 слоёв |
| 2 | Mock API | Контракт + детерминированный режим |
| 3 | Стор и привязки к React | Стор + хук `useLayer` |
| 4 | Команды, кэш и защита от гонок | Все сценарии §6 зелёные в тестах |
| 5 | Панель слоёв (UI) | Рабочий интерфейс по §7 |
| 6 | Доказательство рендеров | Счётчик рендеров + тесты бюджета §8 |
| 7 | Chaos-панель | Ревьюер сам воспроизводит гонки и работу кэша |
| 8 | Стресс-режим 100 / 1000 слоёв | Замеры §10 |
| 9 | Карта | MapLibre + синхронизация без рендеров |
| 10 | Состояние в URL | Ссылка восстанавливает слои |

**Все этапы обязательны.** Сроки не ограничены, поэтому урезать ничего не нужно. Важно другое: этап закрывается, только когда выполнены его критерии готовности, и только после этого начинается следующий. Недоделанный этап 4 испортит впечатление сильнее, чем отсутствие карты.

Issue в upstream vedro — не этап, а отдельное решение заказчика после задачи 0.8 (§15).

## 4. Этапы 1–3 — модель, API, стор

### 4.1 Реестр слоёв (статика)

Реестр хранит то, что **не меняется** во время работы. В сторе этого нет.

| Поле | Тип | Температура | Ветер | Инсоляция |
|---|---|---|---|---|
| `id` | `LayerId` (branded string) | `temperature` | `wind` | `insolation` |
| `title` | string | Температура | Ветер | Инсоляция |
| `unit` | string | °C | м/с | кВт·ч/м²·день |
| `valueRange` | `[min, max]` | −20…+40 | 0…25 | 1…7 |
| `palette` | массив цветов | diverging: синий → белый → красный | sequential: светлый → тёмный синий | sequential: жёлтый → оранжевый |
| `render` | `'fill' \| 'arrows' \| 'heatmap'` | `fill` | `arrows` | `fill` |
| `defaultOpacity` | number 0…1 | 0.7 | 0.9 | 0.6 |

Добавить новый слой = **одна запись в реестре**, ни одной правки в компонентах, сторе или командах. Это критерий масштабируемости №1, и в README он показан на примере.

`LayerId` — branded-тип. Создаётся только через функцию-конструктор реестра, поэтому строка-опечатка не скомпилируется.

### 4.2 Состояние слоя (runtime)

Статус моделируется **discriminated union**, а не набором опциональных полей. Невозможные состояния (например, «ошибка и данные одновременно») не должны выражаться типами.

| `load.kind` | Поля | Смысл |
|---|---|---|
| `idle` | — | Слой выключен или ещё не загружался |
| `loading` | `requestId: number`, `startedAt: number`, `stale: CachedData \| null` | Запрос в полёте. Если в кэше есть свежие данные, они показываются, пока идёт запрос |
| `success` | `data: LayerData`, `loadedAt: number`, `durationMs: number`, `source: 'network'` | Данные получены |
| `error` | `error: LayerError`, `attempt: number`, `stale: CachedData \| null` | Последняя попытка упала. Если есть кэш, показываем его с предупреждением |

`CachedData = { data: LayerData; loadedAt: number }`. Поле `stale` обязательное (`null`, если кэша нет), а не опциональное: так компонент не может «забыть» проверить его наличие.

Полное состояние слоя: `{ enabled: boolean; opacity: number; load: LoadState }`.

Форма стора:

| Ключ | Тип | Зачем |
|---|---|---|
| `ids` | `readonly LayerId[]` | Порядок отображения. Меняется только при смене набора слоёв (стресс-режим) |
| `byId` | `Readonly<Record<LayerId, LayerState>>` | Нормализованное хранение (ограничение V2) |

**Инвариант structural sharing:** при изменении слоя A новым объектом становятся только `byId` и `byId[A]`. Ссылки `byId[B]`, `byId[C]` и массив `ids` не меняются. На этом инварианте держатся все требования по рендерам — он покрывается unit-тестом.

### 4.3 Привязки к React

| Хук | Возвращает | Кто использует |
|---|---|---|
| `useLayer(id)` | `LayerState` конкретного слоя | `LayerRow` |
| `useLayerIds()` | `readonly LayerId[]` | `LayerPanel` (список) |
| `useLayersSummary()` | `{ total, enabled, loading, failed }` — примитивы | Шапка панели, bulk-кнопки |

Требования к хукам:

1. Построены на `useSyncExternalStore` поверх `store.on('@state')` (решает V4). Снимок (`getSnapshot`) берётся из `store.get('byId')`, а не из `store.get()` — иначе новая ссылка на каждый вызов (N1).
2. Сравнение — по ссылке (`Object.is`), без `JSON.stringify` (решает V3).
3. `useLayersSummary` возвращает стабильный объект: новый только при изменении хотя бы одного числа.
4. Unsubscribe защищён от повторного вызова (решает V6).
5. Штатный `useSelector` из vedro в строках слоёв **не используется**. В README — одна строка, почему.

Сам стор и данные остаются в vedro. Мы меняем только способ подписки компонентов, а не менеджер состояния.

### 4.4 Mock API

**Контракт:** `fetchLayerData(id, { signal }) → Promise<LayerData>`.

| Параметр | Значение по умолчанию | Настраивается в Chaos-панели |
|---|---|---|
| Задержка | случайная, 300–2000 мс | ✅ min/max |
| Доля ошибок | 20 % | ✅ 0–100 % |
| Seed генератора | случайный | ✅ фиксированный для воспроизводимости |
| Таймаут | нет | — |

| Поведение | Требование |
|---|---|
| `signal.abort()` | Промис немедленно отклоняется с `AbortError`. Таймер задержки очищается |
| Ошибка | Типизированная: `{ kind: 'network' \| 'server' \| 'timeout'; message: string }`. Текст на русском |
| Данные | GeoJSON `FeatureCollection` — сетка ячеек по территории Кыргызстана (bbox примерно 69.2–80.3° в. д., 39.2–43.3° с. ш., шаг 0.25°). Значения в пределах `valueRange` слоя, с плавным пространственным шумом, а не белым шумом |
| Ветер | Дополнительно `direction` 0–360° в каждой ячейке |
| Детерминизм | При фиксированном seed одинаковые запросы дают одинаковые задержки, ошибки и данные. Без этого тесты гонок нестабильны |

Mock ничего не знает о сторе. Это обычный async-модуль, который можно заменить реальным `fetch` без правок в командах.

## 5. Этап 4 — команды

Вся бизнес-логика — в модуле команд. Компоненты только вызывают команды и читают состояние.

| Команда | Что делает |
|---|---|
| `enable(id)` | `enabled = true`, запускает загрузку |
| `disable(id)` | `enabled = false`, отменяет запрос, `load = idle` |
| `toggle(id)` | `enable` или `disable` по текущему состоянию |
| `retry(id)` | Только из `error`: новая загрузка, `attempt` сохраняется для счётчика, `stale` сохраняется |
| `refresh(id)` | Только из `success`: принудительное обновление, текущие данные уходят в `stale` |
| `clearCache()` | Очищает кэш всех слоёв. Состояние в сторе не трогает |
| `setOpacity(id, value)` | Клампит в [0, 1], пишет в стор |
| `enableAll()` / `disableAll()` | Массово, **одним dispatch** на изменение флагов |
| `retryFailed()` | Retry всех слоёв в `error` |

### 5.1 Защита от гонок — два независимых механизма

| Механизм | Как работает | От чего защищает |
|---|---|---|
| `AbortController` на слой | Хранится в Map вне стора (не сериализуемый объект). `disable` и новый `enable` отменяют предыдущий | Лишние запросы и нагрузка |
| `requestId`-токен | Монотонный счётчик. Перед записью результата проверка: `byId[id].load` в статусе `loading` с тем же `requestId`. Иначе результат отбрасывается | Устаревший ответ, даже если abort не сработал (реальный `fetch` может успеть ответить) |

`AbortError` — **не ошибка**. Он не переводит слой в `error` и не увеличивает `attempt`.

### 5.2 Машина состояний слоя

| Текущее состояние | Событие | Новое состояние | Побочный эффект |
|---|---|---|---|
| выкл / idle, кэша нет | enable | вкл / loading(r1, stale=null) | запрос r1 |
| выкл / idle, кэш свежий | enable | вкл / loading(r1, stale=кэш) | запрос r1, событие «cache hit» |
| выкл / idle, кэш просрочен | enable | вкл / loading(r1, stale=null) | запрос r1, запись кэша удалена |
| вкл / loading(r1) | disable | выкл / idle | abort r1 |
| вкл / loading(r1) | ответ r1 | вкл / success | запись в кэш |
| вкл / loading(r1) | ошибка r1 | вкл / error(attempt+1, stale сохранён) | — |
| вкл / loading(r2) | ответ r1 (устаревший) | без изменений | ответ отброшен, **в кэш не пишется** |
| вкл / error | retry | вкл / loading(r2, stale сохранён) | запрос r2 |
| вкл / error | disable | выкл / idle | attempt сброшен |
| вкл / success | refresh | вкл / loading(r2, stale=текущие данные) | запрос r2 |
| вкл / success | disable | выкл / idle | данные уходят из стора, остаются в кэше |
| вкл / loading | retry / refresh | без изменений | команда игнорируется |
| любое | setOpacity | то же + новая opacity | — |

Таблица целиком переносится в README и покрывается тестами один к одному.

### 5.3 Кэш данных слоя

**Стратегия — stale-while-revalidate.** Задание прямо требует: «при включении слоя — запрос к API». Поэтому кэш **не отменяет** запрос, а убирает пустое состояние: пока идёт запрос, пользователь видит прошлые данные, а не пустую карту.

Вариант «свежий кэш → запрос не отправляем» рассмотрен и отклонён: он нарушает формулировку задания. Он описывается в ADR 006 как альтернатива.

| Параметр | Значение |
|---|---|
| Где живёт | Отдельный модуль `layerCache` в `entities/layer`, **вне стора vedro**. Кэш — не UI-состояние, и ему не нужно оповещать подписчиков |
| Ключ | `LayerId` (в реальном API добавились бы параметры запроса: дата, bbox) |
| Значение | `CachedData = { data, loadedAt }` |
| TTL | 5 минут по умолчанию, настраивается в Chaos-панели. Просроченные данные не показываются и удаляются при чтении |
| Лимит | LRU, 50 записей. Нужен для стресс-режима на 1000 слоёв, иначе память растёт без ограничений |
| Запись | Только при успешном ответе, прошедшем проверку `requestId`. Устаревший ответ не пишется никогда |
| Выключение слоя | Кэш **не очищается** — ради этого он и нужен |
| Хранение между перезагрузками | Нет, только в памяти (IndexedDB — в «что сделал бы дальше») |
| Отключаемость | Переключатель «Кэш вкл/выкл» в Chaos-панели. Нужен, чтобы ревьюер сравнил поведение |

Команды получают кэш через зависимость (параметр фабрики или модульный синглтон с `reset()` для тестов). Иначе тесты начнут влиять друг на друга.

### 7.2 Строка слоя (`LayerRow`)

| Элемент | Поведение |
|---|---|

| Название + единица | Из реестра |
| Бейдж статуса | idle — ничего; loading без кэша — спиннер + «Загрузка…»; loading с кэшем — спиннер + «Обновление · данные 2 мин назад»; success — «Готово · 840 мс»; error — красный «Ошибка»; error с кэшем — «Ошибка · показаны данные 3 мин назад» |

| Кнопка «Повторить» | Только в `error` |
| Кнопка «Обновить» | Только в `success`, иконкой. Вызывает `refresh` |
| Относительное время | «2 мин назад» обновляется раз в 30 секунд **только в строках с кэшем**, без общего таймера на всю панель (иначе перерендер всех строк) |
| Слайдер opacity | Активен только при включённом слое. Значение сохраняется при выключении. Показ в процентах |
| Мини-легенда | Градиент палитры + min/max (из реестра) |

### 7.3 Правила компонентов

| Правило | Причина |
|---|---|
| `LayerRow` получает только `id` | Всё остальное берёт через `useLayer(id)` — стабильные пропсы, `memo` работает |
| `LayerRow` обёрнут в `memo` | Рендер только при изменении своего слоя |
| Никакого `useEffect` для запросов в компонентах | Загрузка — ответственность команд |
| `key` — только `id` слоя | Не индекс |
| Обработчики не создаются заново каждый рендер без причины | Иначе ломается `memo` у детей |

## 8. Этап 6 — бюджет рендеров (критерии приёмки)

Это главная таблица приёмки. Каждая строка — отдельный тест (RTL + счётчик рендеров) **и** видимое поведение dev-оверлея.

| Действие | Кто **может** перерендериться | Кто **не должен** |
|---|---|---|
| Движение слайдера opacity слоя A | `LayerRow A` | Остальные строки, шапка, `LayerPanel`, карта (React) |
| Вкл слоя A | `LayerRow A`, шапка (счётчик «активно») | Остальные строки, `LayerPanel` |
| Ответ API для A | `LayerRow A`, шапка (если меняется число loading/failed) | Остальные строки |
| Ошибка A → retry | `LayerRow A`, шапка | Остальные строки |
| Вкл A с попаданием в кэш | `LayerRow A` — один рендер на `loading(stale)` и один на `success` | Остальные строки. Лишнего рендера «пусто → кэш» нет |
| Тик «N мин назад» в строке A | `LayerRow A` | Остальные строки, шапка |
| `enableAll` | Все строки ровно по одному разу на изменение | Повторные рендеры одной строки на одно событие |
| Любое действие в режиме 1000 слоёв | То же, что при 3 слоях | — |

**Счётчик рендеров** — dev-оверлей: маленькая цифра в углу каждой строки и шапки, увеличивается при каждом рендере. Включается переключателем «Показать рендеры». В продакшн-сборку не попадает. Ревьюер двигает слайдер и видит, что цифра меняется только у одной строки.

StrictMode включён. Двойной рендер в dev учитывается в тестах явно, а не отключением StrictMode.

| Производительность | Анимация зума и панорамирования без просадок при трёх включённых слоях |

### 9.1 `MapSync` — ключевое требование

Синхронизация карты со стором идёт **вне React**: модуль подписывается на стор через `store.on('byId', …)`, сравнивает предыдущее и новое состояние каждого слоя по ссылке и вызывает только нужные методы MapLibre.

Результат: при движении слайдера **0 React-рендеров** компонента карты. Это отдельная строка в README с замером — самый наглядный аргумент по пункту «отсутствие лишних рендеров».

Компонент `MapView` рендерится один раз: создаёт карту, запускает `MapSync`, отписывается при размонтировании (без утечек — проверяется повторным монтированием в StrictMode).

| Запрет | Причина |
|---|---|
| `any`, `as` (кроме `as const` и branded-конструктора), `@ts-ignore`, `!` | Прямое требование задания |
| `dispatch(async …)` из vedro | Результат теряется (V1) |
| Штатный `useSelector` vedro в строках слоёв | O(N) × `JSON.stringify` + tearing (V3, V4) |
| Передача `dispatch` пропсами | Новая функция каждый рендер ломает `memo` (V5) |
| `fetch`/загрузка в `useEffect` компонента | Логика размазывается по UI, гонки не тестируются |
| Бизнес-логика в компонентах | Прямое требование вакансии: разделять UI, логику, состояние, API |
| React Context для состояния слоёв | Ререндер всех потребителей при любом изменении |
| `key={index}` | Ломает идентичность строк при смене набора |
| Отключение StrictMode ради «красивых» счётчиков | Маскирует проблемы, ревьюер заметит |
| Выдуманные цифры производительности в README | Только реальные замеры |
| UI-библиотеки компонентов (MUI, Ant) | Стек — styled-components. К тому же скрывает, как сделаны контролы |
| Переусложнение без строки «зачем» в README | «Без избыточного усложнения» — цитата из вакансии |
| Пропуск запроса при свежем кэше | Задание требует запрос при включении слоя |
| Запись в кэш без проверки `requestId` | Кэш «отравляется» устаревшими данными |
| Кэш внутри стора vedro | Каждая запись оповещает всех подписчиков, а кэш — не UI-состояние |
| Упоминание находок vedro до их подтверждения (0.8) | Ошибочное обвинение библиотеки перед её возможным автором — худший исход |
| Английский в README, ADR, интерфейсе | Решение заказчика: всё на русском |
