**Дата:** 2026-09-26 · **Версия:** `vedro@1.1.0` · **Окружение:** Vitest 5.0.1 + jsdom 30, React 19.3.0, Node 22

Каждая находка — отдельный тест в этой папке. Тест описывает **текущее** поведение библиотеки: если поведение изменится в новой версии, тест упадёт, и решение нужно пересмотреть.

## Подробности

### V1. Async-колбэк в `dispatch`

`lib/helpers/typeCheck.js:16`: `isAsyncFunction` проверяет `fun instanceof Promise`, для функции это всегда `false`. Async-колбэк попадает в синхронную ветку `dispatchWithCB`, результатом считается сам `Promise`. У `Promise` нет собственных полей, поэтому состояние не меняется, а значение, вернувшееся позже, никуда не пишется. Ветка `dispatchWithAsyncCB` недостижима.

Дополнительно: подписчики `@state` получают уведомление, хотя состояние не изменилось.

### V2. Ключи верхнего уровня

`lib/_internal/_DTO.js:26`: `updateParial` сравнивает набор ключей старого и нового состояния и бросает `Dispatch callback have returned wrong object`.

**Уточнение к ТЗ §0:** форма `dispatch(key, value)` ключи не проверяет (`updateByKey`) и новый ключ добавляет. Решение `ids + byId` от этого не меняется: строковую форму для новых ключей не используем.

### V3. Стоимость штатного `useSelector`

`lib/hooks/useStoreSelector.hook.js:8–14`: каждый смонтированный `useSelector` подписан на `@state`. На любой `dispatch` — даже по ключу, который селектор не читает — он вызывает селектор для прошлого и нового состояния и сериализует оба результата. При 50 строках один `dispatch` даёт 100 вызовов селекторов и 102 вызова `JSON.stringify` (+2 — проверка ключей в самом `dispatch`).

Из исходников (тестом не мерилось): сравнение по ссылке вычисляется, но перезаписывается сравнением строк, поэтому стоимость растёт с размером выбранного значения. Для строки слоя с GeoJSON-данными это сериализация всей сетки.

### V4. Подписка в `useEffect`

`lib/hooks/useStoreSelector.hook.js:7–8`: значение берётся в `useState` на первом рендере, подписка — в `useEffect` с пустыми зависимостями.

1. Селектор замыкается на пропсах первого рендера: после смены `id` компонент продолжает показывать старый слой.
2. `dispatch`, случившийся между рендером и подпиской (например, в layout-эффекте соседа), теряется: `on('@state')` сразу вызывает колбэк с одинаковыми `state` и `prevState`, разницы нет, обновления нет. Компонент показывает `0`, в сторе `1`.

### V5. `useDispatch`

`lib/_createVedro.js:52`: `useStore().dispatch.bind(useStore())` — новая функция на каждый рендер. Переданная пропсом в `memo`-компонент, она ломает мемоизацию.

### V6. Повторный unsubscribe

`lib/_internal/_Notifier.js:27–29`: unsubscribe подписки `@state` делает `splice(indexOf(cb), 1)` без проверки индекса. Второй вызов получает `-1`, и `splice(-1, 1)` удаляет последнего подписчика.

**Уточнение:** для подписки на ключ (`on('byId', …)`) индекс проверяется, повторный вызов безопасен. Guard всё равно ставим на обе формы — дёшево и не зависит от деталей реализации.

### V7. Подписка вне React

`store.on('byId', cb)` работает без React. **Уточнения,** важные для MapSync:

- колбэк вызывается сразу при подписке с текущим значением (`'@init'`, `value === prevValue`);
- уведомление приходит на каждый `dispatch`, где ключ есть в частичном состоянии, даже если ссылка не изменилась.

Значит, MapSync обязан сравнивать слои по ссылке сам (ТЗ §9.1 это уже требует) и обработать первый вызов как начальную синхронизацию.

### N1. `get()` возвращает копию

`lib/_internal/_DTO.js:32–33`: `getState()` возвращает `{ ...state }` на каждый вызов. `get('byId')` возвращает ту же ссылку, пока ключ не менялся.

Следствие для §4.3 ТЗ: `getSnapshot` в `useSyncExternalStore` не может быть `() => store.get()` — React получает новый объект на каждый вызов и падает с `Maximum update depth exceeded`. Снимок берётся из `get('byId')` и дальше по ссылке.

С 28.09.2026 решение на штатном `useSelector` ([ADR 009](../adr/009-standard-vedro-api.md)): копия из `get()` сравнивается через `JSON.stringify` результата селектора, а не по ссылке, поэтому цикла нет.

## Ограничение проверки

Тесты запущены в jsdom, а не в браузере: все находки — поведение JS-кода vedro и React, от DOM-движка они не зависят. Решение заказчика от 26.09.2026, ТЗ v1.3.
