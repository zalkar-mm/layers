# ADR 002: Свой хук на `useSyncExternalStore` вместо штатного `useSelector`

**Статус:** Заменено [ADR 009](009-standard-vedro-api.md) (28.09.2026, решение заказчика)
**Дата:** 2026-09-26
**Этап ТЗ:** 3

## Контекст

Штатный `useSelector` vedro (подтверждено в задаче 0.8):

- на каждый `dispatch` вызывает все смонтированные селекторы дважды и дважды `JSON.stringify` (V3): при 50 строках — 100 селекторов и 102 сериализации на одно действие;
- подписывается в `useEffect` с `[]`: селектор замерзает на первых пропсах, обновление до подписки теряется (V4).

## Варианты

| Вариант | Плюсы | Минусы |
|---|---|---|
| Штатный `useSelector` | Ноль своего кода | V3, V4; сериализация GeoJSON-данных слоя на каждое действие |
| Свой хук на `useState` + `useEffect` | Знакомый паттерн | Повторяет V4: tearing и потерянные обновления |
| **`useSyncExternalStore`** | Встроен в React 18+, без tearing, повторно читает снимок после подписки | Снимок должен быть стабильным по ссылке |

## Решение

`useLayer(id)`, `useLayerIds()`, `useLayersSummary()` на `useSyncExternalStore` поверх `store.on('@state')`. Снимок — `store.get('byId')[id]` и `store.get('ids')`, сравнение по ссылке. `store.get()` без ключа для снимка не годится: возвращает новую копию на каждый вызов (N1). Сводка кэшируется и отдаёт прежний объект, пока числа не изменились. Подписка пропускает начальный вызов vedro (V7) и защищена от повторной отписки (V6).

Стор и данные остаются в vedro — меняется только способ подписки компонентов.

## Последствия

- На каждый `dispatch` каждый подписчик делает O(1) чтение по ссылке; перерисовываются только те, чей снимок изменился.
- Решение живёт в `shared/lib/vedro` (подписка) и `entities/layer/model/selectors/hooks.ts` (снимки) — ~60 строк.
- Проверяется тестами `hooks.test.tsx` (одна строка перерисовывается, обновление до подписки не теряется, сводка стабильна).
