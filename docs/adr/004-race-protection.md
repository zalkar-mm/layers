# ADR 004: Двойная защита от гонок — abort + requestId

**Статус:** Принято
**Дата:** 2026-09-26
**Этап ТЗ:** 4

## Контекст

Пользователь переключает слой быстрее, чем приходят ответы (ТЗ §0: «быстро пощёлкает тумблер»). Устаревший ответ не должен «мигнуть» ни на кадр (R2) и не должен попасть в кэш (R12).

## Варианты

| Вариант | Плюсы | Минусы |
|---|---|---|
| Только `AbortController` | Экономит сеть | Реальный `fetch` может успеть ответить до abort — ответ прорвётся в стор |
| Только `requestId` | Надёжно отбрасывает устаревшее | Лишние запросы продолжают идти: 50 кликов = 25 запросов в полёте |
| **Оба механизма** | Сеть и корректность независимо | Два места логики вместо одного |

## Решение

- `AbortController` на слой в `Map` вне стора. Новая загрузка и выключение отменяют прошлый запрос. `AbortError` — не ошибка: слой не уходит в `error`, `attempt` не растёт.
- Монотонный `requestId`. Перед записью: слой в `loading` с тем же `requestId`, иначе ответ отбрасывается — и в стор, и в кэш.
- Переходы — чистые функции (`transitions.ts`): при несовпадении `requestId` возвращают тот же объект, `dispatch` не происходит.

## Последствия

- R1–R8, R12 проверяют оба механизма, в том числе с fetch, который игнорирует abort (R8).
- Проверено мутациями: без проверки `requestId` падают R1 и R8; без abort — R5, R6; с записью в кэш до проверки — R12.
- Счётчик неудачных попыток живёт рядом с abort-контроллерами: в `loading` поля `attempt` нет (§4.2), а retry должен его сохранить.
